HOW IT WORKS NOW
================================================================================

When Admin processes a document:

1. User clicks action button (Accept, Decline, Route, etc.)
2. Frontend validates required fields
3. Confirmation modal appears
4. User clicks "Confirm"
5. Button becomes disabled with spinner
6. Form submits to /admin/inbox/process
7. Backend checks assignment status with optimistic locking
8. If already processed: Shows specific "already processed" message
9. If validation fails: Shows specific validation error
10. If successful: Processes action and shows success message
11. If database error: Shows database error (not "Another request")

TECHNICAL DETAILS
================================================================================

Optimistic Locking:
- Still using WHERE decision = 'PENDING' AND completed_at IS NULL
- Checks rowCount() after UPDATE to detect race conditions
- No FOR UPDATE locks (removed in previous fix)
- Better performance, same safety

Exception Hierarchy:
RuntimeException (extends Exception)
  ↓
InvalidArgumentException (extends RuntimeException)
  ↓
Exception (extends Throwable)
  ↓
Throwable

Catch order matters:
1. Most specific first (RuntimeException)
2. More specific next (InvalidArgumentException)
3. Most general last (Throwable)

Double-Click Prevention:
- JavaScript flag: isSubmitting
- Button disabled after first click
- Visual feedback with spinner
- Form submits only once
